Now we’ll check the editor using a deliberately small example. Replace the body with ten simple words, and compare the displayed count with the actual text. A tiny example is easier to verify than a long article, and it helps us separate a working feature from a number that merely looks plausible. The count in this tutorial uses words separated by whitespace, so punctuation attached to a word does not create an extra word. More sophisticated editors may use different rules, especially across languages.

The reading-time estimate is also transparent. This version divides the word count by two hundred words per minute. That is a convenient assumption for the demonstration, not a measurement of how every subscriber reads. A technical newsletter may take longer because the reader stops to think. An image-heavy newsletter has information that a simple word counter cannot capture. Keep the assumption visible so the estimate is useful without pretending to be exact.

Next, restore the sample draft and add a short practical takeaway. The preview should match what we typed, including paragraph breaks. Then check the local-save message. Local autosave means the draft is stored in this browser on this device. It does not mean the draft has been backed up to your account or synchronized across a team. If you clear browser storage or switch profiles, the saved text may not follow you. For anything important, use an export as well.

The plain-text output is useful when you want the content without formatting. Markdown is useful when your next tool understands lightweight headings and paragraphs. The HTML export is useful for inspecting a formatted document, but you still need to test it in the actual email system you intend to use. A browser page and an email client do not necessarily render the same way. The export is a starting point for that handoff, not proof that every inbox will display it perfectly.

We also need to test text that resembles markup. If I type angle brackets into a draft, the exported document should display that text rather than treating it as executable content. This is why the brief asked for escaping user content. You do not need to memorize the implementation to request the behavior and test the result.

Finally, think about one focused improvement. Perhaps you need a subject-length indicator or a second preview size. Ask for that one change, explain the expected result, and repeat the original checks afterward. A revision can accidentally break something that already worked. The habit we want is simple: build a small tool, use a small test, and keep the useful behavior intact as you improve it.
